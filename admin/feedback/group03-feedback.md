Group 03 – Manta Peer Review  
Strengths:   
The setup experience for Manta was very straightforward and impressive. The README is clear and detailed enough that we were able to clone the repo, install dependencies, and run the first CLI commands in just a few minutes. The commands themselves are intuitive and work as intended, as they follow a consistent pattern that feels natural after reading the docs just once – mt create, mt update, mt delete. Also, when there is an issue with a command, a corresponding error message is returned which helps the users debug what’s wrong with their query. With the SQLite Viewer extension, we can easily visualize the core CRUD workflow which shows the team has a solid data layer foundation. For a CLI-first tool, its simplicity is the winning factor in retaining users and shows that successful software doesn’t always have to be flashy. There is very little user overhead and the learning curve is low for anyone comfortable with a terminal or IDE. 

Improvements:   
The current setup requires Bun to be installed, cloning the repo, and using SQLite Viewer VS Code extension to actually see the issues. While seasoned developers might have no problem with this, many new users may be skeptical to install these dependencies and click off. A lightweight localhost web UI or a (functional) mt view/list command that renders the issues as a formatted table in the terminal would make the tool more self-contained. This can remove the SQLite Viewer dependency entirely. Second, the README documents \--description but the actual build only accepts \--desc, so this mismatch needs to be changed. Third, there’s no feedback for when a command partially fails. For example, running mt update / mt update manta-xxxx with an invalid flag prints an error message but doesn’t tell the user how to fix it unless they go through the README again. An inline command would help greatly and increase efficiency (e.g. mt update \--help). 

Questions:  
Who is the primary intended user for Manta? Since there is no UI and the tool has a CLI-only interface, the suggested audience is developers, but the AIT idea points towards more beginner developers or people who aren’t accustomed to GitHub. Furthermore, beginner developers or even technical PMs are unlikely to clone a repo and run terminal commands. Will Manta be deployed as a real package on npm? Clarifying the target user in the README would help set expectations. 

Suggestions:  
The most impactful next step would be adding a command to spin up a simple localhost web UI showing all issues in a readable format. The reliance on external extensions should be minimalized as much as possible. This would also open the door to browser-based interactions for less technical users who aren’t as comfortable with CLI-only workflows and terminal environments. Also, the command should have multiple valid ways to invoke them, such as \--description, \--descr, \--desc, \--d. This makes it easier for users to make less mistakes, but be careful to not overlap with other existing commands (--d can be mistaken for delete).
